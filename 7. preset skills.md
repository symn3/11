# SillyTavern Chat Completion Roleplay Presets — Reference Skill

## 0. Skill scope and operating rules

This document is a source-grounded technical reference for the original preset files supplied in the conversation and the separately located FF5.4 assets:

1. **LFM Premium Director v6.1 DeepPlan Mind-20**
2. **Pura's Director Preset 15.1 (SillyTavern)**
3. **Geechan — Universal Roleplay / Storywriting v5.2 (Chat Completions)**
4. **FF5.2 Internal States BOLT Setup**
5. **Freaky Frankenstein 5.4** — separately documented Internal States and Hapuppy Forced Reasoning configurations, plus the Regex 3.0 companion suite.

Each preset chapter is an independent knowledge module. Treat its terminology, architecture, activation rules, prompt philosophy and technical implementation as belonging to that preset alone. The document is intended as a design reference for studying how a preset is authored and how its own mechanisms work. It is not a comparison, ranking, synthesis, merge plan, feature-transfer plan or redesign blueprint.

### Rules for using this skill

- Treat the original user-supplied preset sources and the separately linked FF5.4 files as the primary authority for their respective preset-specific facts.
- Use only the chapter for the preset under study. Do not compare it with, rank it against, or combine it with another chapter.
- Preserve original prompt names, identifiers, role values, macro spellings, and tag formats when discussing implementation details.
- Distinguish the prompt's existence from its activation. A prompt can exist in `prompts[]` while being off in a `prompt_order` profile, and default marker prompts can appear without their own text content.
- For a preset export that includes `prompt_order[]`, inspect both `prompts[]` and `prompt_order[]` before reporting the active configuration. Do not infer the effective active setup only from the prompt object's `enabled` field.
- Geechan and FF5.2 were supplied together inside a Markdown paste rather than as two separate attached `.json` files. The pasted JSON is line-escaped and should be treated as source text for analysis, not automatically assumed to be directly importable without normalization and validation.
- When a source does not expose a value, say it is not present in the supplied export. Do not fill gaps with guesses.
- Clearly label interpretations as interpretations. Do not present author claims, model compatibility notes, or token estimates as controlled benchmark results.
- Do not silently reconcile contradictory toggles. Record the exact exported state, then identify the conflict or ambiguity.
- When discussing SillyTavern mechanics, distinguish documented Chat Completion Prompt Manager behavior from assumptions about older exports or version-specific serialization.
- When modifying any preset, preserve stable identifiers and test the final rendered request in Prompt Itemization. The JSON's apparent order is not always the final outgoing message order.

### What “Chat Completion preset” means here

The source structures contain Chat Completion-style message prompts and fields associated with SillyTavern's Prompt Manager, rather than a Text Completion Story String as the primary prompt-construction interface. The Geechan README explicitly labels its design **Chat Completions**. The other three sources use the same Chat Completion preset shape: a list of prompt messages with roles, identifiers, insertion metadata, default prompt markers, generation settings and (where present) extension data.

SillyTavern's official documentation identifies Prompt Manager as the prompt-building interface for Chat Completion APIs; Advanced Formatting / Context Template is the corresponding path for Text Completion APIs. See the references in [Section 12](#12-sillytavern-reference-notes-and-source-links).

## 2. Chat Completion preset JSON: shared anatomy

This section explains the Chat Completion export vocabulary used throughout the reference.

### 2.1 Top-level generation settings

Common or recurring fields include:

|---|---|
| `temperature` | Sampling temperature stored by the preset |
| `frequency_penalty` | Frequency penalty setting |
| `presence_penalty` | Presence penalty setting |
| `top_p` | Nucleus sampling setting |
| `top_k` | Top-k setting; stored as `0` in the supplied source configurations |
| `top_a` | Top-a setting; `0` appears in the supplied configurations |
| `min_p` | Min-p setting; `0` appears in the supplied configurations |
| `repetition_penalty` | Repetition penalty setting |
| `max_context_unlocked` | Exported toggle for the context-size control |
| `tool_reasoning_mode` | Reasoning-mode field; exported as `disabled` in the supplied configurations |

| `openai_max_tokens` | Output-token limit stored by the preset |
| `stream_openai` | Streaming preference in the export |
| `names_behavior` | Character-name handling value |
| `send_if_empty` | Replacement text for an empty send, where configured |
| `impersonation_prompt` | Utility prompt used for the Impersonate action |
| `new_chat_prompt` | Boundary instruction used when beginning a solo chat |
| `new_group_chat_prompt` | Boundary instruction used when beginning a group chat |
| `new_example_chat_prompt` | Boundary instruction for example dialogue blocks |
| `continue_nudge_prompt` | Instruction appended for Continue behavior |
| `group_nudge_prompt` | Group-chat instruction for which character should answer |
| `wi_format` | World Info wrapping template, normally using `{0}` |
| `scenario_format` | Scenario wrapping template, normally using `{{scenario}}` |
| `personality_format` | Personality wrapping template, normally using `{{personality}}` |
| `prompts` | Prompt definitions and default marker prompt entries |
| `prompt_order` | Per-character/profile ordering and activation information, present when the export includes profile-based prompt activation |
| `extensions` | Extension-specific settings, including regex script definitions in these exports |

Some fields are absent from some sources. Do not force a uniform schema onto every export.

### 2.2 Prompt objects

A custom prompt entry may contain some or all of the following:

- `identifier`: stable identifier used by the preset and profile order.
- `name`: UI-facing name inside Prompt Manager. It is an organizational label, not text that should be assumed to be sent to the model.
- `role`: message role such as `system`, `user`, or `assistant`.
- `content`: actual prompt text, often containing SillyTavern macros and prompt instructions.
- `system_prompt`: whether the entry is treated as a system prompt in the export's representation.
- `marker`: indicates a built-in/default prompt slot rather than an ordinary custom text block.
- `enabled`: prompt-level activation flag when provided.
- `injection_position`: exported insertion-position value.
- `injection_depth`: in-chat depth value where applicable.
- `injection_order`: order value for entries sharing role/depth.
- `injection_trigger`: generation-type filter; an empty array in the supplied examples means no explicit trigger restriction is recorded.
- `forbid_overrides`: whether the entry is marked to resist or forbid overrides in the export.

A `marker: true` entry such as `Chat History`, `Char Description`, or `World Info (before)` may have empty content because SillyTavern supplies the corresponding dynamic content at runtime. It is not an instruction to remove the slot.

### 2.3 Prompt order and activation

In exports that use `prompt_order` profiles, the order list references prompt identifiers and carries an `enabled` value for each profile. Therefore:

- A prompt can exist but be disabled in a particular profile.
- The same prompt can be enabled for one profile and disabled for another.
- The prompt object's own `enabled` value is not the only activation information to inspect.
- A built-in marker can be enabled in the order list while containing no literal prompt text in the JSON.
- Profile-specific modes such as single-character, group-chat, and director behavior must not be collapsed into one imaginary universal active stack.

The source profile identifiers include numeric character IDs such as `100000` and `100001`. Interpret them through the included order entries; do not guess their meaning from the numeric identifier alone.

### 2.4 Relative position, in-chat depth and order

The current SillyTavern Prompt Manager documentation describes two key positions:

- **Relative**: the prompt is sent according to its position in the Prompt Manager's drag-and-drop list.
- **In-Chat**: the prompt is inserted inside chat history at a specified depth and uses the selected message role; in this mode it does not follow the ordinary drag-and-drop order.

The documented depth examples are:

- Depth `0`: after the last chat message.
- Depth `1`: before the last chat message.
- Depth `2`: before the second-to-last message.
- Larger depth values move farther back into the history.

For prompts sharing the same role and depth, SillyTavern uses the `Order` value; lower values are sent earlier. The documentation also describes grouping by role, ordered User, AI Assistant, then System. Always inspect the final prompt rather than relying on the file's raw array order.

The supplied exports serialize position using numeric values such as `0` and `1`. Treat the mapping as an export/version convention and verify the imported preset in the running SillyTavern version before making a destructive edit.

### 2.5 Prompt Manager roles and pinned entries

Prompt Manager includes pinned/default slots that cannot be deleted from the selected prompt list, although they may be switched off. Typical pinned entries include Main Prompt, World Info before/after, Persona Description, Character Description, Character Personality, Scenario, Enhance Definitions, Auxiliary Prompt, Chat Examples, Chat History and Post-History Instructions.

This matters when reading exports: a marker entry is not necessarily a custom module, and a custom prompt's name is not necessarily a separate piece of content sent verbatim.

### 3.3 Main prompt philosophy

The main prompt is named **`1 · Ana Motor — Dünya motoru + oyuncu egemenliği`** (`identifier: main`). It defines the model as a text-based RPG engine and living-world simulation. It combines four responsibilities:

1. World simulation: physics, social structure, weather, time and setting behavior.
2. Narration: camera, scene framing and pacing.
3. NPC simulation: independent characters with separate bodies, memories and goals.
4. Causality: consequences follow actions according to established world logic.

The user is the sole player and controls their own character. The main voice rule assigns generated sentences to NPCs and the world, not to the user's unprovided actions, thoughts, feelings or decisions.

Its major sections are:

- **Rules Work in the Background:** instructions should remain invisible; scene details are used only when the moment calls for them, rather than as a checklist.
- **Player Sovereignty:** user dialogue, actions, inner life and choices remain under the user's control. The narration is built from NPC/world-side facts.
- **Priority Order:** safety/platform rules, core engine, hard boundaries and active character module, current user instruction, card facts/personality, continuity, then creative inference.
- **Language:** match the language used by the user unless an explicit output-language module is active.
- **Three Core Principles:** causality, continuity and agency.
- **Revelation Pacing:** secrets and backstory surface gradually; the prompt limits major new revelations per response.
- **Narrative Continuity:** responses can advance a beat, deepen it or preserve a quiet status quo; the `Yes, and / Yes, but / No, but / No, and` pattern helps frame consequences.
- **World Simulation:** the world clock continues, NPCs have independent agendas, and off-screen choices can leave traces.
- **Player Agency — Hard Limit:** the model must not narrate the user's unprovided thoughts, feelings, choices or consent.

The main engine favors consequential but bounded scene movement. It is not simply a request to make every turn more dramatic.

### 3.4 Alternative simplified core

**`simplified-main` — `10 · Basitleştirilmiş Ana Prompt (küçük model; Ana Motor'u kapat)`** is an alternative core for smaller or less instruction-capable models.

It is explicitly intended to replace the main engine, not run in parallel with it. Its content condenses the framework into:

- Core role and simulation responsibility.
- World logic and verisimilitude.
- Style and execution.
- Narration voice and dynamic rhythm.
- Social dynamics and slow-burn pacing.
- Character actions, expressions, thoughts and vocalization.
- Immediate response and independent phrasing.
- Present-scene restraints.

The simplified main is disabled in the supplied solo profile. Its instruction warns that the original engine carries more nuance for stronger models.

### 3.5 Core safety and OOC modules

- **`safety-line` — `1 · Sert Sınırlar — Her zaman açık`:** hard-boundary module. It sets age-related limits for sexualized content, distinguishes dark fiction from real-world operational harm instructions, and states that lower modules cannot override these boundaries.
- **`ooc-handling` — `1 · OOC Ayrımı`:** recognizes message portions framed with `(( ))`, `[[ ]]`, `//` or `OOC:` as out-of-character direction. It says to apply directions without making them diegetic and to answer direct OOC questions separately.

The `safety-line` module is enabled in profile `100000`. It is not present among the enabled items printed for profile `100001`; do not assume both profiles have identical activation merely because the prompt object exists.

### 3.6 Source-reading and setting modules

- **`reading-source` — `2 · Kaynak Okuma — Kart, geçmiş, mesaj`:** interprets World Info as established world truth; Persona as externally perceivable user-character facts; character description/personality as NPC source material; Scenario as the current situation; Example Dialogues as voice examples; and Chat History as continuity evidence. It also explains how user messages are read: quoted text as spoken words, asterisks as action/inner experience, plain text as established narration, parentheses/brackets/OOC as player notes.
- **`card-adapt` — `2 · Kart Tipi ve Ortam Uyarlaması`:** adapts to a single character, multiple characters, scenario/world cards, narrator/game cards, historical setting, technology, species, powers, genre and speech register.
- **`text-medium` — `2 · Metin Ortamı (Göster & Anlat)`:** separates SHOW (concrete sensory evidence) from TELL (plain situational fact), and prioritizes spatial/physical clarity.

### 3.7 Character-count modes

Only one character mode is intended to be active at a time.

- **`mode-single` — `3 · TEK KARAKTER MODU`:** default solo-character portrayal. Includes a character block, an optional external narrator, physical evidence, micro-actions, dialogue behavior, subtext and user-agency limits. The content also has separate adult-content instructions subject to the preset's hard boundaries.
- **`mode-multi` — `3 · ÇOKLU KARAKTER MODU`:** assigns each character an independent mind, agenda and voice. Provides multi-character handling rather than treating all NPCs as one collective speaker.
- **`mode-director` — `3 · YÖNETMEN MODU (Pura)`:** a distinct director-style operation mode. It is not the same as the default single-character mode.

### 3.14 Language and DeepPlan

- **`lang-tr` — `10 · Dil: TR`:** output-language module for Turkish.
- **`scene-plan` — `10 · Derin Plan <plan> + Zihin Belleği (Düşünme Zinciri v2.1)`:** the largest LFM module, approximately 22.8k characters in the supplied JSON.

The DeepPlan module specifies a structured planning block before the visible story. Its documented depth classes are:

- `LIGHT`
- `STANDARD`
- `DEEP`
- `CRITICAL`

It also distinguishes `MODE=BUILD` and `MODE=RECALL`, and has input/scene labels such as speech/action/mixed/narration/OOC/minimal and quiet/tense/turning-point/intense.

Its internal planning sections include:

- `[READ]`: user move, interpretation, what remains unspecified, and world-state delta.
- `[GROUND]`: where/when, physical state, spatial stage, hazards and character knowledge.
- `[CARD]`: character-card synthesis, including drives, fears/wounds, masks, contradictions, tells, limits, social patterns, blind spots, secrets, under-force response and body facts.
- `[MINDS]`: immediate character wants, stakes, interpretations, knowledge, hidden information and emotional drivers.
- `[CAUSALITY]`: feasibility and consequence.
- `[PHYSICS]`: physical outcome and body/environment interaction when relevant.
- `[DECIDE]`: alternative response approaches and a selected direction.
- `[BLUEPRINT]`: opening, beats, character layers, subtext, close and length.
- `[GUARDS]`: likely failure modes and concrete checks.
- `<mindstate>`: the persistent state snapshot.

The module uses confidence labels such as `[C]`, `[S]`, `[P]`, `[?]` and `[X]` to distinguish established facts, strong inferences, provisional claims, unknown facts and contradicted facts. Its BUILD/RECALL distinction is intended to avoid rebuilding the full character interpretation every turn.

The persistent `<mindstate>` is the part designed to survive in the conversation history. It can record a character's core drives/fears/mask/contradiction/tells/limits/under-force response, current mood/intent, relation to user, knowledge, hidden information, open thread and durable physical facts. The prompt emphasizes that temporary state must not be promoted to a permanent personality trait without evidence.

The DeepPlan design relies on regex handling described below. The actual ability to hide or preserve the plan depends on the regex scripts being active in the right context placement and on the model producing the expected tag structure.

### 4.15 Prompt Language & Engineering Profile: Pura 15.1

This section records the actual writing method visible in the Pura JSON. It is a source-specific style profile, not a generic prompt-writing prescription.

**Sentence construction**
- Prefer direct imperative clauses: `Treat`, `Preserve`, `Track`, `Run`, `Advance`, `Drive`, `Keep`, `Ensure`, `Resolve`, `End`.
- State the action first, then add the scope or constraint. Example pattern: “Drive the scene through decisions” followed by a concrete four-part behavior loop.
- Use short-to-medium sentences and compact bullets. A rule usually describes one obligation, one boundary, or one state transition.
- Use absolute terms (`must`, `never`, `only`, `every`) for invariants, but qualify the scope so the rule does not become indiscriminate.
- Keep behavioral rules operational. “Characters are autonomous” is expanded into initiating, refusing, negotiating, withdrawing, committing, and pursuing goals.

**Section engineering**
- Use functional top-level headings (`Directive`, `Continuation`, `Progression`, `Characters`, `Dialogue`, `Causality`, `Social Pressure`, `Narration`, `Environment`, `Tone`, `Scene End`). Each heading owns a distinct responsibility.
- Build a causal sequence into the prompt: immediate goal → resistance → tactical adjustment → concrete result. The model is told what to do next, not merely what quality to imitate.
- Separate scene simulation from prose policing. `Director Main Prompt` governs events and decisions; `Grounded Prose Rules` is a dedicated Post-History quality-control layer.
- Use dialogue as a verb/action system. The prompt lists its functions (pressure, concealment, negotiation, testing boundaries, provoking decisions, changing relationships) rather than relying on vague “natural dialogue” wording.

**Constraint construction**
- Pair a positive instruction with a negative boundary. For example, specify concrete sensory action and then forbid stock metaphors, abstract commentary, or repeated formulas.
- In the Post-History rules, use a hierarchy: `Core` → `Avoid; Never write any of these` → named categories → exact phrase/formula examples.
- Make substitutions explicit: replace a banned phrase, cliché, vague emotion or abstract metaphor with one concrete observable detail. This is more actionable than a bare ban list.
- The Friction Mode variable uses a strong global behavioral tilt, but then constrains its cause: resistance must arise from established history, incentives and social pressure. Record both the forceful directive and its grounding clause.

**Macro and conditional writing**
- Keep optional behavior in discrete blocks and insert it with ST macros such as `{{#if .genre}}`, `{{getvar::friction}}` and `{{setvar::friction::...}}`.
- Treat custom instructions as a named source-of-truth block, not as scattered prose. Preserve the source's explicit precedence statement when documenting that mechanism.

**Verbatim micro-sample and reusable syntax**
- Source phrase: `Drive the scene through decisions.`
- Source pattern: `In every response, make a character pursue an immediate goal, meet resistance, adjust tactics, and produce a concrete result.`
- Post-History pattern: `Write immediate, concrete prose.` followed by `Core` and `Avoid; Never write any of these`.

**When reproducing this writing profile**
1. Start each module with a concrete imperative.
2. Give each heading one job.
3. Turn abstract goals into observable actions or state changes.
4. Use scoped absolutes, not unbounded absolutes.
5. For every major prohibition, provide an acceptable replacement behavior.
6. Keep scene-engine rules out of prose-style cleanup unless the source explicitly combines them.

- Begin with a declarative role frame, then move into directive language. The opening identifies the interaction as collaborative story-writing and defines the model as storyteller/game master before listing its obligations.

- Define both the desired behavior and its conceptual rationale. For example, `bounded rationality` is tied to subjective framing, bias and history, not left as an isolated buzzword.
- Keep the story-context slots conceptually separate from the role and writing contract.

- Start with an explicit timing cue: `Before responding, self-correct:`.

- Give each operation numbered categories and concrete bad examples. This teaches the model what the error looks like instead of relying only on labels such as “avoid clichés.”
- Use conditional checks for scene-specific cases (for example, whether an NPC is brand new) and use ST macros where the response depends on player-supplied custom instructions.

- Main, NSFW and simplified prompts are alternative core prompts, not layers to stack. The source explicitly says to enable only one core prompt at a time.
- Custom player instructions are placed in a conditional block with an explicit precedence statement. Preserve the location and scope of that rule rather than paraphrasing it as a vague preference.

**Verbatim micro-sample and reusable syntax**
- Source phrase: `This is a collaborative story-writing session.`
- Source phrase: `Before responding, self-correct:`
- Source pattern: “Check for any of the following constructions, and remove them entirely”; a separate list then instructs the model to replace other constructions with viable alternatives.

**When reproducing this writing profile**
1. State the conceptual role before the detailed rules.
2. Name each principle and explain its application.
3. Use domain-specific terminology only when the prompt also makes its practical meaning clear.

**Reasoning-task engineering**
- The BOLT block starts with lettered meta-rules (`A`, `B`, `C`, `D`) and then a numbered task sequence (`0` onward).
- Each task is phrased as a question the model must answer or a specific operation it must execute. It also names the exact helper variable or XML block to consult.
- Use conditional skip logic (`if tag is not present`, `skip if inactive`) so optional modules do not become unconditional work.
- Define immutable decisions explicitly (for example, lock a DC before evaluating a roll and never reconsider it later).
- The reasoning prompt repeatedly distinguishes concise planning/checking from drafting the final prose. Record this as the source's intended instruction pattern; do not assume the backend exposes private reasoning merely because the prompt says `think tags`.

**State-output contract**
- The Internal States master prompt specifies exact location (end of response), exact wrappers, required nested sections, spacing and empty-state behavior (`None`).
- The output template is not merely an example: its language frames it as a required schema. The state content is telegraphic and dense, while the surrounding RP prose follows its own prose rules.
- Variables such as `bondsTemplate`, `invTemplate`, `chekhovTemplate`, `thoughtsTemplate`, `gmNotebookTemplate`, `dndTemplate` and `worldsimTemplate` are inserted into the shared state wrapper. The prompt's output grammar and regex layer therefore form a coupled contract.

**Modular author-comment technique**
- Many toggles begin with a natural-language comment explaining why to enable/disable the module, which model behavior it targets, and whether it costs tokens or reasoning time.
- Keep author-facing comments distinct from the actual runtime instruction block. A comment such as “turn this on if...” is documentation; the tagged rule block beneath it is the model-facing contract.
- Preserve alternative CoT modules as separate selectable blocks rather than combining their full contents into one instruction sequence.

**Verbatim micro-sample and reusable syntax**
- Source phrase: `Never draft prose; brainstorm only.`
- Source pattern: `A. Reason briefly ... B. Execute all tasks ... C. Generate final response ...`.
- Source pattern: `If listed XML tag is not present, skip it.`

**When reproducing this writing profile**
1. Define the simulation contract in a compact key/value block.
2. Use named XML scopes for independent subsystems.
3. Turn complex reasoning into numbered tasks with explicit helper references.
4. Make conditional modules explicitly skippable when inactive.
5. Define machine-readable state output as a schema, not a loose suggestion.
6. Keep author comments, runtime instructions, state templates and regex rendering responsibilities distinguishable.

## 7.2 Freaky Frankenstein 5.4 Internal States — source-specific design module

- Rules are often written as compressed imperatives and short bullets. The prose modules also use concrete bad/good examples and exact numeric limits.
- The preset uses strong modal language (`Must`, `Never`, `Strictly`, `ONLY`, `exactly`) and explicit exceptions (`dialogue exempt`, `skip if tag absent`, `unless...`). Record the exception as part of the rule; do not keep only the absolute wording.
- Author comments above toggles explain purpose, expected model fit, token cost and activation advice. They are not always part of the actual behavior contract; distinguish comment text from the XML-tagged runtime instruction.

**Prose and dialogue wording patterns**
- The prose modes define their scope before listing style rules. Cinematic Realism, for example, explicitly scopes the rules to narrative prose and exempts spoken NPC dialogue.
- Style rules are expressed as compact categories: realism/flow, sentence structure, body/movement, banned formulas/styles.
- Bans are often demonstrated through `BAD` and `GOOD` examples, then followed by a positive replacement instruction.

- POV blocks use a terse `Mode` / `Tense` / `Address` structure and then rules. Hybrid POV explicitly separates third-person world narration from second-person user sensations and provides a bad/good example to protect the distinction between sensation and action.

**Internal States output grammar**
- The master block instructs the model to append raw HTML at the end of every response.
- It requires every section in the template to remain present; empty or unchanged sections are represented as `None` rather than silently omitted.
- It defines exact spacing, a dense telegraphic style inside the state block and `<!-- GFX_START -->` / `<!-- GFX_END -->` wrappers.
- The template contains nested `<details>` panels for NPC agendas, NPC locations, factions, bonds, quests and variable-inserted modules, followed by physics/engine/world state.

## 7.4 FF5 Regex 3.0 Suite — source-specific implementation module

**Role**
- The suite is the presentation and cleanup companion for the 5.4 prompt output. It is not a substitute for the prompt's state schema or for the frontend's native rendering behavior.
- Its rules operate on the generated message text and use SillyTavern regex-script metadata such as `placement`, `disabled`, `markdownOnly`, `promptOnly` and `runOnEdit`.

**Observed script families**
1. Untagged-thought cleanup: `FF5 Delete - Untagged Thoughts` and `FF5 Catch - Untagged Thoughts` target text preceding the Time header when the model emits reasoning without the expected tags.
2. GFX/code-fence repair: `FF5 Repair - GFX Trailing Unfence` and `FF5 Repair - GFX Unfence` repair stray Markdown fences around GFX/internal-state/details structures.
3. Dialogue presentation: Tremble, Measured, Whisper and Shout dialogue regexes convert tagged speech into spans with distinct visual treatment; the universal dialogue colorizer handles the base color tag.
4. Thought handling: `Hapuppy Delete Thoughts` removes recognized think/reasoning/internal-monologue blocks; `Hapuppy Hide Thoughts` wraps recognized thought sections in collapsible HTML.
5. State UI formatting: menu scripts style Internal States, quests/Chekhov/inventory/GM Notebook and NPC agenda/location/faction/bond panels; other scripts stack bullets and highlight GM Notebook markers.
6. Relationship visualization: relationship-bar scripts turn bond/sparks/grudge text into visual meters/cards.

**Regex engineering patterns**
- Use bounded, case-insensitive patterns that tolerate spacing variation and multiple possible closing-tag forms.
- Capture only the text needed for the replacement and preserve it through `$1`, `$2`, etc. The HTML replacement owns presentation; the prompt owns the semantic tag vocabulary.
- Use `markdownOnly: true` for visual HTML transformations that should operate on rendered Markdown content, and `promptOnly: true` for cleanup intended to affect prompt/history text. Never assume these flags are interchangeable.
- Thought cleanup and thought hiding are different operations. Deletion removes the matched block; hiding preserves it inside a collapsible `<details>` wrapper. Do not enable both blindly without understanding execution order and placement.
- GFX repair rules specifically address malformed fences around `GFX_START`, `GFX_END`, `<internal_states>` and `<details>` structures. Preserve the wrapper grammar emitted by the prompt.

**Operational cautions**
- Regex scripts are order-sensitive. A cleanup rule that runs before a display rule may remove the material the display rule expects.
- Test the suite with: correctly tagged thought, untagged thought before Time header, malformed GFX fence, nested `<details>`, each dialogue delivery tag, empty state section and relationship record.
- Validate behavior in the actual SillyTavern version. Regex syntax support and script placement may change across frontend versions.

# 9. Regex scripts: how to document and troubleshoot them

Regex scripts are an extension/presentation layer and are not the same thing as the prompt body itself. In these presets they:

- Convert structured tags such as `[NPC:...]`, `[SCENE]`, `[ITEM]`, `[CHOICES]` or `[DIRECTIONS]` into formatted UI output.
- Hide or remove internal state, thoughts, image prompts or planning blocks from display or prompt context.
- Collapse HTML details blocks or apply highlights/relationship bars.
- Trim choice or direction sections to keep the conversation context cleaner.

For each script, inspect at least:

- `scriptName`
- `findRegex`
- `replaceString`
- `placement`
- `disabled`
- `markdownOnly`
- `promptOnly`
- `runOnEdit`
- `substituteRegex`
- `minDepth`
- `maxDepth`

A script can be present but disabled; it can also run only in a specific placement or at selected depths. Do not treat a script name alone as evidence of its exact runtime behavior. Read the actual regex, replacement string and flags.

# 10. Prompt debugging and verification workflow

Use this workflow whenever the user asks why a preset behaves differently than expected.

1. **Identify the exact preset and active API.** Confirm Chat Completion is selected, not Text Completion.
2. **Read the exact preset source.** Do not rely on a preset name, remembered version, or previous summary.
3. **Inspect top-level settings.** Record sampling, context/output values, streaming and reasoning-related settings.
4. **Inspect prompt entries.** Identify markers versus custom text, roles, identifiers, injection positions, depth/order and override flags.
5. **Inspect profile order.** If the export contains `prompt_order`, resolve the active profile and list its enabled identifiers.
6. **Identify mutually exclusive groups.** Examples: single/multi/director mode; POV; user-writing; length; prose voice; main/NSFW/simplified cores; Story/Cinematic; MAX/BOLT/Micro.
7. **Inspect macros and variables.** Confirm that every `getvar` has a corresponding setter or default where expected. Check conditional branches and exact variable spelling.
8. **Inspect regex scripts.** Match their expected tags, placement, flags and depth to the produced output.
9. **Inspect the rendered request.** Use SillyTavern Prompt Itemization, terminal logs or browser console to determine what the model actually receives.
10. **Run a fresh-chat control test.** Chat history strongly affects style and behavior; changes to the main prompt may not reset patterns already learned from prior messages.
11. **Change one factor at a time.** Do not simultaneously alter the core prompt, role, insertion order, reasoning settings, sampling and regex scripts.
12. **Preserve a rollback copy.** Save the edited prompt itself and then save the Chat Completion preset. Prompt-level save and preset-level save are separate operations in the documented UI.

### Minimum test scenarios

For a technical sanity check, use a small test set that includes:

- Single NPC conversation with a short spoken line.
- User physical action with a clear spatial consequence.
- Two NPCs with conflicting immediate goals.
- Group chat with more than one participant.
- Character who does not know a hidden fact.
- Scene jump/time passage and an object/injury that should persist.
- Quiet slice-of-life exchange with no forced complication.
- A scene with an optional tracker/choice module activated.
- Continue/regenerate/impersonate operations.
- A turn where no state should change, to test whether memory systems invent changes.

Evaluate user agency, card fidelity, dialogue voice, knowledge boundaries, physical continuity, state correctness, pacing, prose repetition, token cost and output formatting separately.

# 11. Troubleshooting patterns specific to these presets

## 11.1 The model ignores a module

Check whether it is enabled in the active profile, whether its position is relative or in-chat, whether its role is accepted by the backend, and whether another later instruction overrides it.

## 11.2 The model follows the wrong user-control contract

Check the selected preset's user-authorship contract and any enabled user-writing option. Inspect its own control identifiers, OOC authorization and active prefill.

## 11.3 NPCs know facts they should not know

Check card/world knowledge separation, the active anti-omniscience module if present, state-block leakage and whether author-only state has been mistakenly placed where NPCs can read it as in-world knowledge.

## 11.4 Memory/tracker facts drift

Check whether the tracker is active; whether its output tag survives; whether regex removes it from the prompt; whether the state is copied forward; whether the model is asked to emit a full snapshot or only a diff; and whether it has invented unsupported changes.

## 11.5 The prompt becomes repetitive or over-restricted

Inspect the selected preset's active anti-slop, banned-word and prose-style modules. Several restrictive modules active at once can overconstrain prose; verify the selected preset's own profile and module instructions.

## 11.6 The model outputs hidden plan/state HTML visibly

Check the relevant regex script's active state, `promptOnly`/display placement flags and matching tags. A hidden HTML `<details>` block is still text in the transcript; the regex layer determines whether it is hidden, transformed, or stripped in a particular surface/context.

## 11.7 Output length changes unexpectedly

Check the selected length module, `openai_max_tokens`, any active model-side reasoning budget, post-history rules, and whether the active preset profile differs from the one being tested.

## 16.1 Purpose and boundaries

This chapter defines a reusable architecture for studying, organizing, validating and eventually authoring modular SillyTavern Chat Completion roleplay systems. It is an architecture skill, not a ready-made preset, JSON export, character card or instruction to merge every feature from the source presets.

The source-specific chapters above remain independent records of what each preset actually contains. This chapter is the cross-source architecture layer. Clearly distinguish source-derived observations from recommendations introduced here.

The architecture preserves the native SillyTavern Chat Completion model:

- Prompt definitions remain separate entries with stable identifiers, names, roles, content, injection positions, depth/order and supported flags.
- The active outgoing stack is determined by the selected Prompt Manager configuration, not by prompt names or a visual divider.
- The model-facing request must be checked in Prompt Itemization after import or modification.
- Regex scripts remain a separate extension, presentation and history-processing layer. They do not replace semantic prompt rules.
- Variables and conditional macros may be used where supported, but their evaluation order and behavior must be tested in the installed SillyTavern version.

The objective is controlled modularity: modules stay independently editable while profiles, exclusivity rules, dependencies, precedence and bounded recovery reduce accidental conflicts.

## 16.2 What the supplied presets actually demonstrate

| Mechanism | Source evidence | Actual capability |
|---|---|---|
| Alternative base prompts | Geechan Main / NSFW / Simplified; LFM Main / Simplified Main; Pura Director / Simplified Director | Alternative engines intended to be selected, not stacked |
| Mutual-exclusion warnings | Geechan README; FF5 divider prompts and prose/POV/NSFW/CoT selectors; Pura combined randomizer notes | User guidance only; not a technical lock |
| Profile-specific activation | LFM and Pura contain multiple prompt_order entries with different character_id values | Distinct active prompt lists can be represented |
| Variable-gated behavior | Pura uses setvar/getvar and conditionals; Geechan separates player instruction variables | Optional prompt text can be conditionally inserted when the macro path supports it |
| Late constraint layer | Pura and Geechan Post-History Prose Rules | High-influence response constraints with model-dependent effects |
| Persistent state structures | FF5 Internal States; LFM DeepPlan/Mindstate; Pura trackers | Explicit state schemas and continuity records |
| Regex cleanup and presentation | Pura, FF5.2 and FF5.4 suites; LFM plan/mindstate regex | Deterministic text transformations for known patterns |
| Endpoint-specific forced format | FF5.4 Hapuppy Forced Reasoning | Visible output protocol, not a universal private reasoning channel |

### Warnings are not locks

A divider named Pick one or a comment saying Only enable ONE is documentation. It does not prevent a user from enabling two conflicting prompts. A prompt's enabled property, its presence in prompts[], and its active entry in the selected prompt_order are separate facts. A regex script being present does not prove it is active.

Do not claim automatic conflict resolution unless the active configuration contains a tested mechanism that actually gates conflicting content.

## 16.3 Architecture layers

These are logical responsibilities. They do not all need to become separate SillyTavern prompt messages.

| Layer | Responsibility |
|---|---|
| A. Core Contract | Stable role, agency, canon, causality, knowledge and OOC invariants |
| B. Profile Composition | A validated bundle of compatible modules for one use case |
| C. Module Library | Independently authored engine, POV, prose, dialogue, tracker and format modules |
| D. Conflict Policy | Exclusive groups, dependencies, precedence and fallback |
| E. State Contract | Canonical state schema, update policy and retention priorities |
| F. Observation and Repair | Detection and bounded recovery of known failures |
| G. Rendering and Cleanup | Regex/UI transformations synchronized with output tags |
| H. Verification | Prompt Itemization checks and behavioral regression tests |

Do not collapse these layers into one enormous Main Prompt. The Main Prompt establishes the simulation contract; specialist modules define optional behavior.

## 16.4 Layer A — Core Contract

The Core Contract is the short set of invariants shared by every supported profile. It should define only:

1. Role and task: what the model simulates.
2. User authorship: who controls the user's character, and what explicit exceptions are permitted.
3. Canon and source priority: established card, scenario, world and chat facts are not casually overwritten.
4. Causality and continuity: actions have feasible consequences; time, position, injuries, objects and commitments persist.
5. Knowledge boundaries: each NPC acts only on information it plausibly possesses.
6. OOC handling: out-of-character directions are separated from in-world events and handled according to a declared priority.
7. Output ownership: what the model writes and what must remain open for the user.

Authoring rules:

- Use direct, operational instructions rather than abstract quality slogans.
- State each invariant once in the Core Contract. Specialist modules may explain implementation, but must not redefine it.
- Distinguish hard boundaries from style preferences.
- Keep POV, prose voice, length, genre, reasoning format, tracker schemas and UI markup out of the Core Contract.
- Scope absolute terms precisely.
- Keep the Core Contract model-agnostic; place endpoint assumptions in compatibility notes or profile modules.

The Core Contract may draw inspiration from LFM's engine, Pura's Director Main Prompt, Geechan's Narrative Consistency and FF5's system state. Do not copy their complete Main Prompts into it or imply that their different philosophies are identical.

## 16.5 Layer B — Profile Composition

A profile is a named, tested set of module selections. It is not another prompt style or a second simulation engine. It selects one compatible base engine and adds only the overlays needed for its use case.

Recommended profile vocabulary:

| Profile | Intended use | Composition |
|---|---|---|
| Lite | Fast, simple roleplay; smaller or less instruction-capable models | Core + one compact engine + essential agency/continuity rules; no heavy trackers or visible reasoning protocol |
| Standard | Everyday character-driven RP | Core + one engine + one POV + one user-control policy + one prose baseline + essential continuity aids |
| Immersive | Deeper world simulation and persistent state | Core + one engine + NPC knowledge/agency/physics + selected trackers + matching output/regex |
| Director | User acts as scene director/co-writer | Core + one Director engine + explicit director/user authorship contract + selected scene progression and continuity tools |

These are proposed profile names, not profiles already present in the source exports. Each implemented profile must map to exact prompt identifiers and active flags.

For every profile, record:

- Stable profile key and human-readable name.
- Intended use and tested model/backend.
- Exactly one selected base engine.
- Exactly one selection from each exclusive group used by that profile.
- Optional modules enabled and modules intentionally disabled.
- Required regex scripts, flags and placement.
- Required variables/macros and defaults.
- Expected output format.
- Estimated prompt cost, clearly marked as unmeasured until verified.

### Three SillyTavern implementation routes

**Route 1 — Separate Chat Completion preset exports.**  
Create one saved preset per supported profile. Each export has a complete, unambiguous active prompt list. This is the clearest route when users need a real profile choice and must not accidentally combine alternatives. Preserve stable prompt identifiers across exports where practical.

**Route 2 — Existing prompt_order entries.**  
Where an export already contains multiple prompt_order entries, treat each as a separate activation map. LFM and Pura demonstrate different active lists associated with different character_id values. Do not call this a general profile dropdown unless the installed UI actually exposes that behavior. Verify how the target SillyTavern version selects the active order.

**Route 3 — Variable-gated modules.**  
A selector variable can conditionally include one profile branch or one alternative module, following patterns in Pura and Geechan. This is reliable only when the macros are supported in that prompt path and the selector is set before dependent content is evaluated. Validate macro evaluation order in the installed version. Variable gating can stop multiple branches from contributing, but it is not a native visual lock on Prompt Manager toggles.

Use divider prompts and Only enable ONE notes for onboarding, not as the sole enforcement mechanism.

Recommended default policy:

- Never activate two base engines in one profile.
- Never activate two alternatives from the same exclusive selector group.
- Keep optional modules off unless their dependencies are satisfied.
- If a selection is invalid, use the profile's declared fallback or report the conflict; do not invent a hybrid.
- Permit custom modules only when they declare compatibility with the selected profile.

## 16.6 Layer C — Module Library and module contracts

Every module must have one bounded job. Use a consistent manifest in documentation or a sidecar file:

| Field | Meaning |
|---|---|
| identifier | Stable unique SillyTavern prompt identifier |
| name | Prompt Manager label |
| purpose | One-sentence behavior change |
| category | Core, engine, POV, user-control, prose, dialogue, realism, genre, tracker, reasoning, format, UI or cleanup |
| role | Actual prompt role |
| position | Relative or In-Chat |
| depth/order | Actual configured values where relevant |
| profiles | Profiles in which the module is allowed |
| exclusive_group | Selector group, or none |
| conflicts_with | Incompatible module identifiers |
| requires | Required prompts, variables, macros or regex scripts |
| output_contract | Tags, headings, fields or state schema expected |
| regex_dependencies | Exact scripts and required flags/placement |
| fallback | Behavior when a dependency or format is unavailable |
| cost | Estimated token/context cost |
| source | Original preset and source section |

This manifest is documentation, not permission to add arbitrary fields to native SillyTavern prompt objects. Keep unsupported metadata in this skill, a README or a sidecar manifest.

Each model-facing module should define:

1. Scope: when it applies and what it does not control.
2. Behavior: concrete actions or decisions expected from the model.
3. Constraints: boundaries specific to the module.
4. Compatibility: modules it can coexist with.
5. Output format: only if it introduces tags or structured output.
6. Fallback: what happens when required data or dependencies are missing.

Keep author-facing comments (purpose, model fit, activation advice and token cost) distinct from runtime instructions.

## 16.7 Layer D — Exclusivity, dependencies and conflict resolution

### Exclusive groups

The following selector groups are supported by patterns in the supplied sources:

| Group | Examples | Rule |
|---|---|---|
| Base engine | LFM Main/Simplified; Pura Director/Simplified; Geechan Main/NSFW/Simplified variants | Select one |
| Simulation mode | Single / Multi / Director where offered as alternatives | Select one compatible mode |
| User authorship | Write for User / Don't Write for User; FF5 Anti-parrot / Embellish | Select one user-control contract |
| POV | First / Second / Third / Hybrid | Select one |
| Prose style | Story / Cinematic; alternative named voices | Select one primary prose baseline |
| Content mode | Realism / Freaky or other alternatives | Select one, or none |
| Reasoning protocol | MAX / BOLT / Micro; native vs forced visible format where incompatible | Select one, or none |
| Response length | Short / Balanced / Long / Flexible | Select one |
| Echo policy | Anti-parrot / Anti-echo vs Embellish | Select one |
| Dialogue presentation | Competing color/output formats | Select one if grammars conflict |

Not every module pair is exclusive. Trackers may coexist if they own different state domains or share a declared schema. They conflict when they duplicate ownership of a field, demand incompatible output formats or contradict the selected behavior contract.

### Conflict classes

- **Hard conflict:** two contracts cannot both be true, such as Write for User and Never Write for User.
- **Dependency conflict:** a module is selected without its required template, variable, macro or regex companion.
- **Output-schema conflict:** two modules require incompatible formats for the same output region.
- **Priority conflict:** a late/high-influence rule contradicts a core invariant. Fix the offending module rather than repeating both rules.
- **Resource conflict:** combined prompt/state footprint exceeds the measured context budget.
- **Model compatibility conflict:** the selected endpoint cannot support the assumed reasoning or formatting protocol.

### Resolution order

1. Platform and provider constraints.
2. Core Contract and hard user-authorship/OOC boundaries.
3. Exactly one base engine.
4. Exactly one choice from every active exclusive group.
5. Required simulation, knowledge and physics modules.
6. POV, prose, dialogue and length overlays.
7. Selected state trackers and their schemas.
8. Compatible reasoning/output protocol, if any.
9. Presentation and regex transformations.
10. Optional genre, randomizer and decorative modules.

This is a configuration policy, not a claim that SillyTavern technically enforces semantic priority. The actual outgoing sequence depends on Prompt Manager roles, triggers, Relative/In-Chat position, depth and order. The model may still interpret conflicts imperfectly.

### Injection position and precedence

- Keep the compact Core Contract in the base/system layer.
- Place specialist instructions where their responsibility makes sense.
- Use Post-History Instructions for a concise final constraint/check layer, not as a dumping ground. Pura and Geechan show that these rules can be influential and model-dependent.
- Do not assume numeric injection_position values map identically across all exports or versions.
- Do not equate prompts[] array order with the final outgoing order.
- Verify the imported UI and Prompt Itemization. Prompt Manager documentation describes Relative ordering and In-Chat depth behavior; check the installed version rather than guessing.

## 16.8 Layer E — State Contract and long-context survival

### One source of truth per state domain

Before enabling trackers, declare who owns each fact. If Time Tracker owns current time, another module must not independently rewrite it in a conflicting format. If Bonds owns relationship values, do not run a second tracker with another scale.

Each state domain must define:

- Canonical field names and allowed values.
- Whether it stores current state, event history or both.
- Events permitted to change the state.
- Which character knows the information.
- Whether a fact is public, NPC-private, author-only or unknown.
- How unchanged, empty and unknown values are represented.
- Which prompt module writes it.
- Which regex script formats or removes it, if any.
- How it survives into future prompt history.

### Snapshot, delta and rebuild

Use a hybrid policy:

- **Canonical snapshot:** compact current facts required to continue the scene.
- **Turn delta:** only meaningful changes caused by the latest response.
- **Open threads:** unresolved promises, threats, clues, plans and consequences that must survive.
- **Rebuild rule:** if the snapshot is missing or invalid, reconstruct only from supported chat/card/world facts and mark uncertainty as unknown.

The source set demonstrates different strategies: FF5 uses a structured Internal States template with empty sections; LFM separates transient plan material from compact persistent Mindstate; Pura uses optional typed trackers. These are not interchangeable schemas. Select one state architecture per profile and document any deliberate bridge.

### State update rules

- Update a field only when the scene provides evidence.
- Do not promote a temporary emotion into a permanent personality change without evidence.
- Do not infer a relationship score change from one ambiguous line.
- Do not move an NPC, change an injury, transfer an item or advance time without a supported event.
- Keep who knows a fact separate from whether the fact is true.
- Keep author-only secrets out of NPC-facing knowledge.
- If no state change occurred, preserve the prior value.
- Use the selected schema's explicit Unknown/None convention consistently.

### Context pruning priority

When the context budget is tight, preserve:

1. Core canon and user-authorship contract.
2. Current location, time and physical positions.
3. Persistent injuries, important possessions and physical constraints.
4. NPC goals, relationships and knowledge boundaries relevant to the current scene.
5. Open plot threads, promises, clues and consequences.
6. Recent events needed to interpret the current interaction.
7. Optional flavour trackers, decorative UI and low-relevance history.

Pruning may remove redundant old prose, duplicated summaries and expired temporary details. It must not silently delete a consequential open thread or turn an unknown fact into a known one.

### Context-saver warning

A regex that strips Internal States, GFX wrappers or thought blocks may reduce prompt length but can also remove the only copy of state. Before enabling a prompt-only stripper, verify what exact text remains in the rendered prompt and where the retained snapshot comes from. Presentation hiding, history cleanup and persistent memory are different jobs.

## 16.9 Layer F — Observation and Repair Loop

### Capabilities and limits

A prompt cannot inspect the actual backend request or guarantee that a model followed every rule. Regex can repair known textual patterns; it cannot reliably resolve semantic contradictions or reconstruct missing world facts. A model-authored self-check is a behavioral instruction, not a deterministic validator.

Use three separate mechanisms:

**1. Preventive checks before output.**  
The selected core and modules check user agency, canon, causality, knowledge boundaries, physical continuity, active mode, state changes and required output grammar. Keep the check concise and skip inactive modules.

**2. Deterministic formatting repair.**  
Use regex only for known, testable syntax problems: a recognized missing closing tag, stray code fence around a known wrapper, known heading variation or predictable malformed tracker line. Each rule needs a bounded match, clear replacement, correct placement and correct markdownOnly/promptOnly/runOnEdit flags. Avoid broad patterns that may delete narrative text.

**3. Semantic recovery on the next turn.**  
When a state block is incomplete or contradictory, instruct the model to:
- Recover only unambiguous fields from the latest valid snapshot and supported chat events.
- Preserve unknown or disputed fields as unknown.
- Apply only supported changes.
- Re-emit the canonical state schema.
- Keep narration separate from state repair.
- Avoid exposing internal checklist text unless the user requests an OOC diagnosis.

### Event-driven health checks

Do not assume a prompt can reliably count every user/model turn or schedule a background check. A rule such as every 5–8 turns is dependable only if a tested counter increments exactly once for the intended generation types. Regenerations, swipes, Continue, group-chat paths and quiet generations may affect counting.

Prefer event-driven checks at meaningful boundaries:

- Scene or location transition.
- Time skip.
- Major injury, possession or relationship change.
- New NPC or faction entering the scene.
- Major clue or secret revealed.
- Summary/context-pruning operation.
- Detected malformed or missing state section.

Add a periodic counter only after validating generation triggers, variable persistence and macro evaluation order.

### Recovery severity

| Failure | Recovery |
|---|---|
| Missing optional decorative panel | Omit it or emit the schema's empty marker |
| Malformed known HTML wrapper | Apply a narrow regex repair and test nested details |
| Missing required state fields | Rebuild supported fields from last valid state and chat evidence; mark the rest unknown |
| Contradictory state values | Prefer the most recent supported event; retain ambiguity if evidence is insufficient |
| Conflicting active modes | Do not improvise a hybrid; use the declared profile fallback or flag invalid configuration |
| Lost critical continuity | Reconstruct from available history/card/lore only; state uncertainty rather than fabricate |
| Endpoint cannot support selected protocol | Disable the incompatible protocol and use the profile's normal response path |

## 16.10 Layer G — Regex and output-contract coupling

Whenever a prompt emits tags or structured state, treat its output grammar and regex scripts as one versioned interface.

For every output tag, record:

- Exact opening and closing syntax.
- Whether nesting is allowed.
- Whether empty sections are emitted or omitted.
- Whether the block is visible to the user.
- Whether it is retained in prompt history.
- Which regex scripts match it.
- Whether the script transforms, hides or deletes it.
- What happens when the model emits a partial or malformed tag.

Rules:

- A visual formatter is not a semantic state store.
- A thought hider is not native private reasoning.
- Delete and collapse/hide operations are different; enabling both without testing execution order can remove material before a display rule handles it.
- markdownOnly and promptOnly are not interchangeable. A display formatter should not unexpectedly mutate history; a context stripper should not be assumed to hide visible output.
- Script names do not prove behavior. Inspect findRegex, replaceString, placement, depth and flags.
- Any prompt change that affects tags requires regression tests for its regex suite.

## 16.11 Layer H — Model-specific adaptation

The architecture is portable; every implementation is not. Keep the Core Contract model-agnostic and maintain a compatibility record for each endpoint family.

Test separately:

- Instruction hierarchy adherence.
- Behavior as prompt length and history depth increase.
- Whether one selected mode stays isolated from alternatives.
- State schema and exact tag adherence.
- Sensitivity to Post-History instructions.
- Whether a forced visible reasoning format is useful, ignored or leaks into narrative.
- Whether the backend supports the selected native reasoning feature.
- Output-length and verbosity drift.
- Dialogue quality, prose repetition and user-agency violations.

Do not infer compatibility from historical model lists or model names alone. Visible forced reasoning headings do not prove a private reasoning channel. Backend reasoning settings and prompt-authored reasoning protocols are separate.

## 16.12 Layer I — User-facing module experience

- Group related prompts under clear divider labels.
- Use consistent prefixes for category and alternative.
- Explain purpose, model fit, token cost and dependencies in concise author comments.
- Mark true alternatives with SELECT ONE and list the exact competing prompt names.
- Mark optional overlays separately from required modules.
- Keep custom instructions in one clearly named location.
- Avoid forcing beginners to manage dozens of toggles when a profile can bundle the common configuration.
- Keep an expert profile for manual control, but make the default profile small and coherent.

UI labels are documentation only. The active profile configuration remains the source of truth.

## 16.13 Validation workflow

1. Inventory every prompt identifier, role, content, active flag, injection setting, macro, variable, output tag and regex dependency.
2. Classify base engines, exclusive selectors, composable overlays, state writers, reasoning protocols and presentation helpers.
3. Build an exclusivity matrix and list dependencies separately.
4. Compose each profile with one base engine and one choice from each active exclusive group.
5. Validate dependency closure: every variable has a defined/default value; every special output tag has a contract; every required regex is active with correct flags.
6. Validate prompt role, triggers, Relative/In-Chat position, depth and order.
7. Inspect Prompt Itemization to confirm the exact outgoing request, including history, world info, character/persona data and late instructions.
8. Run fresh-chat regression tests before judging long contaminated histories.
9. Test short, medium and long histories, including summarization/pruning and state reconstruction.
10. Change one factor at a time.
11. Record tested model, backend, SillyTavern version, date and settings.
12. Preserve rollback copies of the preset and regex suite.

### Minimum regression suite

| Test | What it checks |
|---|---|
| User gives an action but no reaction | Model does not invent the user's next action or decision |
| NPC lacks access to a hidden event | Knowledge boundary |
| Two NPCs want incompatible outcomes | Independent goals and causal resistance |
| Quiet everyday scene | No forced escalation from optional randomizers |
| Physical location/time changes | Spatial and temporal continuity |
| No meaningful state change | Tracker does not invent changes |
| State field changes after a clear event | Correct field changes once, with cause |
| New NPC appears | Character source and knowledge rules |
| One alternative selected | Competing variants remain inactive |
| Conflicting modes enabled in a test copy | Conflict detection/fallback |
| Output tag malformed | Regex repairs only the intended defect |
| Prompt-only state stripper active | Required continuity state still reaches the next request |
| Continue, Regenerate, Swipe and group-chat paths | Trigger/counter behavior |
| Long conversation summarized/pruned | Canon and open threads survive without fabrication |

### Evaluation rubric

Track separately:

- User agency violations.
- NPC knowledge-boundary violations.
- Character-card/source fidelity.
- Causal and physical continuity.
- State accuracy and unsupported state changes.
- Exclusive-mode conflicts.
- Prose repetition and generic dialogue.
- Output grammar and regex repair success.
- Prompt token cost measured from the rendered request.
- Quality and rule adherence across models and history lengths.

Record test counts, observed failures and exact model/backend. Do not claim improvement without before/after testing.

## 16.14 Implementation anti-patterns

Avoid:

- One giant Main Prompt that makes modules hard to select and test.
- Divider-only exclusivity presented as technical enforcement.
- Every module enabled by default.
- Multiple base engines active together.
- Stacked POV or user-control contracts.
- Unbounded Post-History rules that overpower the base prompt.
- One universal CoT block that ignores endpoint differences.
- Regex treated as a semantic repair engine.
- Multiple trackers owning the same fact.
- Stripping the only surviving state copy.
- Trusting stored context limits as proof of backend capacity.
- Treating an exported toggle as active without inspecting the selected profile.
- Treating author comments as model-facing instructions.
- Testing only one model and one short conversation.

## 16.15 Completion checklist

A modular design is not ready until:

- [ ] The Core Contract is short and shared by every profile.
- [ ] Every profile selects exactly one base engine.
- [ ] Every exclusive group has a declared set of alternatives.
- [ ] The active configuration has no unresolved hard conflicts.
- [ ] Dependencies and macro variables are listed.
- [ ] Every module has a clear scope and fallback.
- [ ] Every state domain has one source of truth.
- [ ] Snapshot, delta and pruning behavior are documented.
- [ ] Output tags and regex scripts form a tested contract.
- [ ] Semantic recovery and regex formatting repair are not conflated.
- [ ] The actual Prompt Itemization has been inspected.
- [ ] Fresh-chat and long-context regression tests have been run.
- [ ] Model/backend/version limitations are recorded.
- [ ] Original source presets remain preserved as independent references.
